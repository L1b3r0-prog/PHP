## 1. Introduction to PHP

**What PHP actually is.** PHP (PHP: Hypertext Preprocessor) is a server-side scripting language. "Server-side" is the key idea: the PHP code never reaches the visitor's browser. The web server runs the PHP code, and only the *output* of that code (usually plain HTML) is sent to the browser. This is why "View Source" on a PHP-generated page never shows PHP syntax — by the time the browser sees anything, PHP has already finished running.

**Embedded language.** PHP is described as an embedded language because PHP code can be mixed directly into an HTML file, switching in and out using `<?php ... ?>` delimiters. A single `.php` file can freely interleave HTML, CSS, JavaScript, and PHP blocks. This matters conceptually because it means PHP isn't a separate program that "generates" a webpage from scratch — it's more like a templating engine woven into HTML.

**Case sensitivity — a common trap.** PHP keywords, function names, and class names are case-*insensitive* (`echo`, `Echo`, and `ECHO` all work). But **variable and constant names are case-sensitive** (`$Name` and `$name` are two different variables). This asymmetry is a classic source of bugs and a classic exam trap.

**Typing model.** PHP is a *loosely typed* (dynamically typed) language by default: you don't declare a variable's type, and its type can change as the program runs (a variable holding a string can later be reassigned an integer). This is contrasted with *strongly/statically typed* languages, where a variable's declared type is fixed and enforced by the compiler. PHP 7+ lets you opt into stricter behaviour with `declare(strict_types=1)`, which makes function argument type-hints strictly enforced rather than being silently coerced.

**Data types.** PHP has simple/scalar types (`string`, `int`, `float`, `bool`, `null`) and composite/reference types (`array`, `object`), plus a special `resource` type that represents a handle to something external, like an open file or database connection. Understanding *why* `resource` exists is useful: PHP can't represent an open file handle as a normal value, so it wraps it in an opaque reference instead.

**Variables vs constants.** A variable ($ prefix) can be reassigned at any time. A constant, created with `define()` or `const`, cannot change once set. The practical distinction to remember: `const` is evaluated at compile time and can only be used at the top level of a script (not inside functions, loops, or conditionals), while `define()` is a runtime function call and can be used anywhere, including conditionally.

**Arrays as PHP's one true collection type.** Unlike many languages that separate "lists" from "dictionaries"/"maps", PHP uses a single `array` type for both. Every PHP array is technically an *ordered map* of keys to values — when you use sequential integer keys starting at 0, it behaves like a classic indexed array; when you use string keys, it behaves like an associative array (dictionary). This unification is why functions like `foreach ($arr as $key => $value)` work identically regardless of which "flavour" of array you're using.

**Operator precedence and associativity.** Precedence decides which operator "binds tighter" when multiple operators appear without parentheses (e.g. `*` before `+`). Associativity decides the order when operators of *equal* precedence appear together — left-to-right or right-to-left. Assignment operators are right-associative (`$a = $b = 5` assigns 5 to $b first, then to $a), while most arithmetic operators are left-associative.

## 2. Functions and Control Structures

**Why functions exist.** A function packages a reusable block of logic under a name, so it can be invoked repeatedly without duplicating code. A **procedure** is really just a function that performs an action (like printing) but doesn't hand a value back via `return`— the distinction is purely about whether `return` is used to produce a result the caller can use.

**Value vs reference — the conceptual model.** When you pass an argument normally, PHP copies the value into the function's local scope. Any changes inside the function happen to that copy, not the original. This is safe by default because it prevents functions from silently mutating data the caller didn't expect to change. Passing by reference (`function f(&$x)`) breaks that isolation deliberately: the parameter becomes an alias for the *same* variable in the caller's scope, so mutations propagate back out. This is a deliberate escape hatch, used when a function's entire purpose is to modify the caller's variable (e.g. sorting functions like `sort()` work this way internally).

**Variadic functions.** The `...` syntax lets a function accept an arbitrary number of arguments, which are automatically collected into an array inside the function. This solves the problem of not knowing in advance how many inputs a caller will supply — instead of overloading multiple function signatures (which PHP doesn't support the way some languages do), a single variadic function handles all cases.

**Default values and named arguments work together.** Default parameter values let you skip optional arguments; named arguments (PHP 8) let you specify *which* parameter you're supplying a value for, by name, instead of relying on position. This means you can skip over some optional parameters while still supplying a later one, without needing to pass placeholder values for the ones in between. The rule to remember: required parameters must still all be supplied somehow, but the *order* becomes flexible once you're using names.

**Type declarations and union types.** PHP 7 introduced optional type hints on parameters and return values. By default, PHP tries to coerce a mismatched type into the declared one where possible (e.g. a float `4.8` passed to an `int` parameter is truncated, with a deprecation warning). With `declare(strict_types=1)`, that coercion is disabled and a type mismatch becomes a fatal `TypeError` instead. Union types (`int|float`) let a single parameter or return type legally be more than one type, which is useful when a function is *intentionally* meant to handle either.

**Variable scope — the core idea.** A variable's scope is the region of code where it exists and can be referenced. PHP function bodies are "sealed" from the surrounding script by default: a variable declared outside a function is invisible inside it, and vice versa. This is a deliberate design choice to prevent functions from accidentally depending on or corrupting unrelated parts of a script. The `global` keyword is an explicit opt-in that breaks this isolation for one specific variable, telling PHP "inside this function, treat this name as referring to the global variable of the same name, not a new local one."

**Static variables.** Normally, a local variable inside a function is recreated (and reset) every time the function is called. Declaring it `static` changes this: PHP preserves its value between separate calls to the same function, as if the variable "remembers" its last state. This is especially useful in recursive functions, where you want a counter or accumulator that persists across the recursive call chain without threading it through every function parameter.

**Control structures — the underlying logic.** `if/else` picks one branch based on a boolean condition. `switch` compares one expression against multiple candidate values using loose comparison (`==`), and by default "falls through" to subsequent cases unless a `break` is used — this fall-through behaviour is a historical quirk carried over from C-style languages, and forgetting `break` is one of the most common bugs. `match` (PHP 8) was introduced specifically to fix switch's rough edges: it uses strict comparison (`===`), never falls through, and is an *expression* that directly returns a value rather than requiring you to assign inside each branch.

**Loop structures and when each fits.** `while` checks its condition *before* running the loop body, so the body might never execute. `do...while` checks *after*, guaranteeing at least one execution — useful when you need to do something once regardless, then decide whether to repeat (e.g. showing a menu, then asking "again?"). `for` is really syntactic sugar that bundles initialisation, condition, and update into one line, and is idiomatically used when the number of iterations is known or countable in advance. `foreach` is specifically for iterating over arrays (or other iterables) without manually managing an index.

**include/require — why two pairs of near-identical statements exist.** Both pull the contents of another file into the current script, effectively as if you'd pasted the code in place. The difference is entirely about failure behaviour: `include` treats a missing file as non-fatal (a warning, and the script continues), while `require` treats it as fatal (a fatal error that halts the script). The rule of thumb: use `require` for files essential to the script working at all (e.g. a database connection file, a core class definition) and `include` for optional, non-critical content. The `_once` variants exist to solve a different problem entirely — re-inclusion — which matters most when the included file declares a function or class, since PHP cannot redeclare the same function/class twice without a fatal error.

## 3. Manipulating Strings & Handling User Input

**Single vs double quotes — not just a style choice.** In a double-quoted string, PHP actively parses the string's contents, looking for variables to interpolate and escape sequences to convert (like `\n` becoming an actual newline). In a single-quoted string, PHP does almost none of this — the content is nearly literal, with only `\\` and `\'` recognised. This has a real performance and correctness implication: single quotes are marginally faster (no parsing needed) and safer when the literal text might accidentally contain something that looks like a variable reference.

**Why escape characters exist.** Certain characters have structural meaning in PHP syntax (quotes delimit strings, `$` begins a variable name). An escape character (`\`) tells PHP "treat the next character as a literal, not as syntax." This is necessary whenever the literal text you want to include would otherwise be misinterpreted, e.g. an apostrophe inside a single-quoted string.

**Why htmlspecialchars() matters beyond "cleaning up" text.** When user-submitted text is echoed back into an HTML page unmodified, any HTML or JavaScript the user typed becomes *live* — the browser can't tell the difference between "text the developer wrote" and "text a user typed that happens to look like a `<script>` tag." This is the basis of Cross-Site Scripting (XSS) attacks. `htmlspecialchars()` converts the characters that give HTML its structural meaning (`<`, `>`, `"`, `'`, `&`) into inert HTML entities, so they display as visible text instead of being parsed as markup. The general principle worth remembering: *any* time untrusted input is echoed back into an HTML context, it needs escaping.

**$_GET vs $_POST — a design tradeoff, not just a syntax difference.** GET data is appended to the URL as a query string. This makes GET requests bookmarkable, shareable, and cacheable, but limits how much data can be sent (URL length limits) and means the data is visible in browser history, server logs, and the address bar — unsuitable for sensitive data. POST data travels in the request body, invisible in the URL, with no practical size limit, but the request itself isn't bookmarkable or naturally repeatable. The choice between them is a statement about the *nature* of the action: GET should be used for requests that only retrieve/view data (idempotent, safe to repeat), POST for requests that submit or change something.

**Regular expressions — the mental model.** A regex pattern describes a *shape* that a string can match, built from literal characters and metacharacters (special symbols with structural meaning). Anchors (`^`, `$`) pin the match to the start/end of the string rather than letting it match anywhere inside. Quantifiers (`?`, `+`, `*`, `{n,m}`) control *how many times* the preceding element may repeat. Character classes (`[...]`) let a single position in the pattern match any one of several alternatives. Grouping (`(...)`) lets a whole sub-pattern be treated as one unit, both for applying quantifiers to a multi-character sequence and for capturing that portion of the match separately.

**Why preg_match() is more powerful than plain string functions.** Functions like `str_contains()` or `strpos()` only test for a literal, fixed substring. A regex pattern can express a *category* of valid strings (e.g. "exactly 4 digits", "starts with http, optionally https") without knowing the exact text in advance — this is essential for validating structured input like emails, postcodes, or phone numbers, where the *shape* matters more than the exact characters.

**Form handlers and the request/response cycle.** A web form's `action` attribute names the script that will process submitted data; its `method` attribute decides whether that data arrives via `$_GET` or `$_POST`. The receiving script (the "form handler") typically performs three jobs in sequence: validate the incoming data (is it present, is it the right format), process it (calculate something, store it), and produce a response (confirmation, error message, or the next page). Validation deliberately happens **server-side** even if client-side (JavaScript) validation also exists, because client-side checks can always be bypassed by a user who disables JavaScript or crafts a request manually.

## 4. Files and Directories

**File permissions — what the numbers actually encode.** Every file/directory has three permission *subjects* — the owning User, the owning Group, and Other (everyone else) — and three permission *actions* — Read, Write, Execute. Each octal digit in a permission value like `0754` encodes one subject's combined permissions as a sum: Read=4, Write=2, Execute=1. So `7` = 4+2+1 = read+write+execute, `5` = 4+1 = read+execute (no write), `4` = read only. The leading `0` isn't a permission at all — it's a fixed marker for the whole permission number's format.

**Why permissions matter conceptually.** A web server process runs as a particular user (e.g. `www-data`), and file permissions determine what that process is *allowed* to do to a given file, independent of what the PHP code tries to do. This is a security boundary: even flawless PHP code can be blocked from reading/writing a file if permissions don't allow it, and conversely, permissions set too loosely can let a compromised script do more damage than intended.

**Reading directories — two approaches, one underlying idea.** `opendir()`/`readdir()`/`closedir()` is the manual, low-level approach: open a handle, pull one entry at a time in a loop until there are no more, then close the handle. `scandir()` is a convenience wrapper that does all of this internally and just hands back a complete array. Both approaches will return the special `.` (current directory) and `..` (parent directory) entries that every directory implicitly contains — code almost always needs to filter these out explicitly.

**Streams as PHP's general model for reading/writing.** A "stream" is an abstraction for any source/destination you read from or write to sequentially — most commonly a file, but also things like network connections. The `fopen()`/`fread()`/`fwrite()`/`fclose()` family works around a *handle*, a reference to that open resource, and a *pointer*, PHP's internal bookmark of "where in the stream am I right now." Reading advances the pointer forward; you don't need to track position manually. The *mode* string passed to `fopen()` (`r`, `w`, `a`, `x`, and their `+` variants) controls both the intended operation (read/write) and the starting pointer position, plus whether existing content is preserved or erased. This matters a lot practically: opening with `w` mode instantly erases the file's existing content, even before you've written anything new.

**The convenience functions vs the stream functions.** `file_get_contents()`, `file_put_contents()`, `readfile()`, and `file()` all exist because, for the common case of "read/write the *whole* file in one go," manually managing `fopen`/`fclose` is unnecessary overhead. The stream functions remain necessary when you need fine control — reading line-by-line for a huge file that shouldn't be loaded entirely into memory, or writing incrementally as data becomes available.

**File uploads — why the process has extra steps.** An uploaded file doesn't land directly where the developer wants it. The web server first stores it in a temporary location (exposed to PHP via `$_FILES[...]['tmp_name']`), and this temporary file is deleted automatically at the end of the request unless the script explicitly relocates it with `move_uploaded_file()`. This two-step process (temp location → permanent location) exists so the server can validate and clean up uploads safely, without files landing directly in a permanent, potentially publicly accessible location before any checks have run. `enctype="multipart/form-data"` is required on the form because the default form encoding can't represent binary file data.

**Downloading files outside the public directory.** Normally, any file inside a website's public folder can just be linked to directly. Files stored *outside* that folder (often deliberately, to prevent direct/unauthenticated access) need PHP to act as an intermediary: the script reads the file server-side and streams its contents back to the browser, disguised with `header()` calls that tell the browser how to treat the incoming data (as a downloadable attachment, with a given filename, size, and encoding) rather than trying to render it inline. The strict requirement that headers be sent before any other output exists because HTTP headers must physically precede the response body in the raw network response — once any content (even accidental whitespace) has been sent, the headers section is already closed.

## 5. Arrays

**Arrays as PHP's universal collection.** As mentioned in section 1, PHP doesn't distinguish "lists" from "maps" at the type level — an array is always a set of key→value pairs, internally ordered by insertion. An "indexed array" is just the common case where the keys happen to be sequential integers starting at 0.

**Mutating from the ends — why four different functions.** `array_push()`/`array_pop()` operate on the *end* of the array (add/remove respectively); `array_unshift()`/`array_shift()` operate on the *beginning*. The push/unshift functions return the array's new element count; the pop/shift functions return the value that was removed. A key detail: adding/removing from the *beginning* forces PHP to renumber every subsequent numeric key, which is comparatively more expensive than operating at the end — a subtle but real performance consideration if arrays are large.

**Why unset() leaves gaps.** `unset($arr[$key])` simply deletes that one key from the array; it does not shift or renumber anything else. This means an indexed array can end up with non-contiguous numeric keys after an `unset()` (e.g. keys 0, 2, 3 with 1 missing). `array_values()` exists specifically to "repair" this by returning a new array with fresh sequential keys, discarding the old ones — useful after any operation (unset, array_unique, filtering) that might leave gaps.

**slice vs splice — the distinction that's easy to mix up.** `array_slice()` is *read-only*: it returns a new array representing a portion of the original, and the original is untouched. `array_splice()` *mutates* the original array in place, simultaneously letting you remove a portion and/or insert new elements at that position. If you only need to *read* a subsection, use slice; if you need to *change* the array's actual contents, use splice.

**Sorting — value vs key, and whether associations survive.** `sort()`/`rsort()` sort by value and **discard** the original keys, renumbering from 0 — appropriate for plain indexed arrays where key identity doesn't matter. `asort()`/`arsort()` also sort by value but **preserve** the original key-value pairing — necessary for associative arrays where the key (e.g. a name) needs to stay attached to its value (e.g. a score) after sorting. `ksort()`/`krsort()` sort by *key* rather than value entirely, useful when the natural order of the array should follow its keys (e.g. alphabetical by name) rather than the values.

**Two-dimensional (and multidimensional) arrays.** Since any array value can itself be another array, "2D array" isn't a distinct language feature — it's simply an array whose elements are arrays. This generalises naturally: a value can be an array of arrays of arrays, and so on, to represent arbitrarily nested/tabular data. Accessing a specific value means chaining index/key access for each level, e.g. `$data['Cups']['pints']`.

**Arrays in Web forms.** Giving multiple form inputs the *same* `name` attribute, with `[]` appended (e.g. `name="answers[]"`), tells PHP to collect every submitted value with that name into a single array under that key in `$_POST`/`$_GET`, rather than the later inputs overwriting the earlier ones (which is what would happen without the brackets). This is the mechanism behind any form that submits a variable number of related values — checkboxes, repeated question fields, multi-select inputs.

## 6. Object-Oriented Programming — Part 1 (Classes & Objects)

**The core OOP idea.** A class is a *template* describing what data (properties) and behaviour (methods) something has; an object is one concrete *instance* created from that template, with its own independent copy of the property values (though shared method code). This separation lets you define a concept once ("what is a BankAccount") and create as many independent instances of it as needed, each with its own state.

**Why access specifiers exist.** `public`, `private`, and `protected` control which code is allowed to read/call a given property or method from outside. This isn't about security in the network sense — it's about *encapsulation*: hiding a class's internal representation so external code can only interact with it through a deliberate, controlled interface. This lets the class's author change the internal implementation later without breaking code that depends on it, as long as the public interface stays the same. The general design guideline in the notes — properties private/protected, methods public where they need external use — reflects this: data is typically hidden, behaviour is typically exposed.

**Why protected exists as a "middle ground."** `private` is invisible even to child classes, which sometimes is too restrictive — a subclass often legitimately needs access to a parent's internal state to extend its behaviour. `protected` allows that access within the inheritance family while still blocking arbitrary *external* code, which `public` wouldn't do.

**$this and why it's necessary.** Inside a method, `$this` refers to the specific object the method was called on. Since a class's method code is shared across every object created from it, there needs to be some way for the method to know *which* object's properties it should read or modify when it's actually running — `$this` is that reference.

**Constructors — automatic initialisation.** `__construct()` runs automatically the moment `new ClassName(...)` is executed, before any other code can interact with the object. Its purpose is to guarantee an object starts in a valid, fully-initialised state rather than requiring the caller to remember to call a separate "setup" method afterward. Constructor Property Promotion (PHP 8) is a syntax shortcut: writing the visibility modifier directly on a constructor parameter (`public function __construct(private float $balance)`) both declares the property AND assigns the incoming argument to it in one line, removing the previously-required boilerplate of declaring the property separately and writing `$this->balance = $balance;` by hand.

**Destructors — the mirror image.** `__destruct()` runs automatically when an object is being destroyed — typically at the end of the script, or explicitly via `unset()`. Its purpose is cleanup: releasing resources the object was holding onto (open file handles, database connections) that wouldn't otherwise be freed automatically.

**Accessor/mutator methods — why not just make properties public?** If a property is public, any external code can set it to *any* value, including invalid ones (e.g. a negative account balance). By making the property private and exposing controlled `get`/`set` methods instead, the class can enforce validation rules (like the `setBalance()` example only accepting positive values) and can change how the value is stored internally without changing how external code interacts with it.

**__get() and __set() — a step further.** These "magic methods" intercept attempts to read/write a property that isn't directly accessible (private/protected) using the ordinary `$obj->property` syntax, rather than requiring explicit `getProperty()`/`setProperty()` calls. They let external code use natural-looking property syntax while the class still runs custom logic behind the scenes — useful for validation, logging, or computed properties, without changing how the class is *used* from the outside.

## 7. Working with Databases Using PHP

**Why a database instead of files.** Databases add automated indexing (fast lookup without scanning everything manually), controlled redundancy, built-in multi-user support, and structured backup/recovery — capabilities that would otherwise need to be built by hand on top of plain files.

**mysqli as PHP's primary MySQL interface.** `mysqli` ("MySQL Improved") replaced the older, deprecated `mysql` extension and supports both procedural and object-oriented usage; the object-oriented style (`new mysqli(...)`) is the modern convention. A connection object represents an open, authenticated link to the database server, through which all further queries are issued.

**Why exceptions became the default error-handling model.** Historically, mysqli functions returned `false` on failure and errors had to be checked manually after every call. Since PHP 8.1, mysqli throws a `mysqli_sql_exception` automatically on failure instead. This is a meaningful shift: it means errors can no longer be silently ignored by accident (an uncaught exception halts the script loudly), and `try`/`catch` becomes the standard way to handle expected failure points (like a connection that might not succeed) gracefully instead of crashing the whole script.

**What query() actually returns, and why it varies.** For statements that only perform an action without producing rows (`CREATE TABLE`, `INSERT`, `UPDATE`, `DELETE`), success is reported simply as boolean `true`. For statements that *retrieve* rows (`SELECT`, `SHOW`), the return value is instead a result-set *object*, because there's now actual data to hand back, which needs its own methods (`fetch_assoc()`, `fetch_row()`, etc.) to step through.

**fetch_row() vs fetch_assoc().** Both retrieve the *next* row from a result set (advancing an internal pointer, similar in spirit to a file pointer), and both return `null` once there are no more rows — which is exactly what makes `while ($row = $result->fetch_assoc())` a natural loop-until-exhausted pattern. The only difference is how the row's fields are keyed: `fetch_row()` gives a plain numbered array (`$row[0]`), `fetch_assoc()` gives an associative array keyed by column name (`$row['email']`), which is more readable and less fragile if column order changes.

**insert_id and affected_rows — reading "what just happened."** After an `INSERT` into a table with an `AUTO_INCREMENT` primary key, the database generates that key automatically — `insert_id` is how PHP retrieves the ID that was just assigned, since the script itself never specified it. `affected_rows` answers a related but different question — after an `INSERT`, `UPDATE`, or `DELETE`, how many rows did this statement actually change — useful for confirming an operation had the expected effect (e.g. detecting that an UPDATE's WHERE clause matched zero rows, which usually indicates a bug).

**Why prepared statements exist — three separate justifications.** (1) *Performance*: when a similar query runs many times, the database can parse and optimise the SQL structure once (during `prepare()`) and simply re-execute it repeatedly with different parameter values, rather than re-parsing full SQL text every time. (2) *Bandwidth*: subsequent executions only need to send the changed parameter values over the network, not the entire SQL statement text again. (3) *Security*: this is the most important one conceptually. When SQL is built by concatenating raw variables into a string (`"...WHERE id=" . $id`), a malicious value in `$id` can inject additional SQL that the database will execute as *code*, not data — this is SQL injection. Prepared statements avoid this entirely because parameter *values* are always transmitted and treated as inert data by the database driver, never as part of the SQL syntax itself, no matter what characters they contain.

## 8. Managing State Information

**Why this is a problem at all.** HTTP, the protocol underlying the web, was designed to be *stateless*: each request a browser makes is handled independently, with the server retaining no memory of previous requests from that same visitor by default. This is a deliberate simplicity trade-off in HTTP's original design, but it conflicts with almost everything a modern website needs to do — remembering a logged-in user, a shopping cart, a user's preferences. "Maintaining state" is the general term for the various techniques PHP provides to work around this built-in statelessness.

**Hidden form fields — the simplest, most limited mechanism.** Since a `<form>` submission already carries its named input values to the next script, a hidden `<input type="hidden">` field can smuggle along an extra piece of data the user isn't meant to edit directly (like a record ID). Its scope is extremely narrow: the data only survives for that one form submission and is gone afterward. It's also fully visible and editable by the user (via "View Source" or browser dev tools), so it must never be trusted for anything sensitive or security-relevant.

**Query strings — slightly broader, still not persistent.** Appending `?key=value&key2=value2` to a URL lets data travel with a *link* rather than a form submission, readable via `$_GET`. Like hidden fields, this only lasts for the single request that URL represents — following the link again without the parameters loses the data. Its main advantage over hidden fields is that it works with plain hyperlinks, not just form submissions, and the resulting URL is bookmarkable/shareable (which is sometimes exactly the point, sometimes a privacy problem).

**Cookies — the first mechanism with real persistence.** A cookie is a small piece of data the *server* asks the *browser* to store, which the browser then automatically re-sends on every subsequent request to that domain. This is what makes cookies capable of surviving across multiple separate page visits, not just one request-response cycle. **Temporary cookies** are stored only in the browser's memory and vanish when the browser closes; **persistent cookies** are written to a file on disk and survive a browser restart, lasting until their specified expiry time. The crucial timing rule: `setcookie()` must run before *any* other output, because it works by adding to the HTTP response headers, and headers must be sent before the body — this is the exact same constraint as the `header()` function discussed in section 4. A subtler gotcha worth internalising: a cookie set with `setcookie()` during the *current* script execution is **not** yet available in `$_COOKIE` during that same execution — it only becomes readable on the *next* page load, once the browser has actually stored it and sent it back.

**Deleting a cookie — there's no explicit "delete" function.** Instead, you call `setcookie()` again with the same name and an expiry time set in the *past*. The browser interprets an already-expired cookie as one it should discard immediately, which achieves deletion indirectly.

**Sessions — server-side state instead of client-side.** A session works almost the opposite way to a cookie: rather than storing the actual data on the client, PHP stores the data in a file on the *server*, and only a short, opaque session ID is given to the client (usually via an automatically-set `PHPSESSID` cookie) to identify which server-side file belongs to them on future requests. `session_start()` either creates a brand-new session (generating a fresh ID) or resumes an existing one (if a valid session ID was received), transparently populating `$_SESSION` with whatever was previously stored under that ID. Because the actual data lives server-side, sessions work even if a client has cookies completely disabled, as long as the session ID is instead passed manually — typically appended to URLs via the `SID` constant.

**Why session variables behave differently from cookies regarding immediate availability.** Since `$_SESSION` is just a PHP array populated directly from server-side storage during `session_start()`, and doesn't depend on a browser round-trip the way `$_COOKIE` does, session variables you set are immediately visible in `$_SESSION` within that very same script execution — no reload needed, unlike the cookie gotcha above.

**The comparison that ties this section together:** hidden fields and query strings are single-request mechanisms with no real persistence; cookies persist by storing data on the *client*; sessions persist by storing data on the *server*, with only an identifying token on the client. Choosing between cookies and sessions in practice comes down to: does the data need to survive the browser closing (favor cookies), and is the data sensitive enough that it shouldn't sit in the client's browser at all (favor sessions).

## 9. Object-Oriented Programming — Part 2

**Inheritance — solving code duplication.** When several classes share common structure and behaviour but also have their own unique aspects, inheritance (`class Child extends Parent`) lets the shared logic be written exactly once, in the parent, and automatically reused by every child, rather than copy-pasted into each. A child automatically gains access to all non-private members of its parent and can additionally define members of its own. Critically, this relationship is one-directional: a parent class has no awareness of, or access to, anything defined in its children — the parent must remain generic enough to make sense on its own.

**Overriding — customising inherited behaviour.** A child class can redefine a method that already exists in the parent, replacing the parent's implementation with its own for objects of that child class. This is how a shared "shape" of behaviour (every class in the hierarchy has an `area()` method, say) can still produce type-specific results. Prefixing a parent's method with `final` is a way to explicitly forbid this — declaring "no child class is allowed to override this particular method," useful when a method's correctness depends on it never being changed.

**Constructors in an inheritance chain.** If a child class doesn't define its own constructor, it automatically inherits and uses the parent's. But the moment a child *does* define its own constructor, the parent's constructor is **not** called automatically alongside it — inheritance doesn't chain constructors implicitly. If the child's constructor still needs the parent's setup logic to run, it must explicitly call `parent::__construct(...)`. The same applies to destructors.

**Polymorphism — the payoff of overriding.** Polymorphism means that code written to work with a *general* type (e.g. "any Shape") can, at runtime, actually be operating on any of several more *specific* types (Circle, Square) — and calling the same method name on each will trigger that specific object's own overridden version, without the calling code needing to know or care which exact subclass it's dealing with. This is what makes patterns like "loop through an array of mixed subclass objects, calling the same method on each" work cleanly.

**Abstract classes — enforcing a contract while still sharing code.** An abstract class can mix fully-implemented methods (shared logic) with abstract methods (signature only, no body) that every concrete child *must* implement. It can never be instantiated directly — it only exists to be extended. This is useful when there's genuinely some shared implementation to offer, but also some behaviour that only makes sense to define per-subclass (like `area()`, which is meaningless without knowing the specific shape).

**Interfaces — a contract with zero shared implementation.** An interface only declares method *signatures*, with no implementation of any kind, and a class agrees to that contract using `implements`. The key structural difference from abstract classes: a class can implement *multiple* interfaces at once (since there's no actual code being inherited, there's no conflict), but can only extend *one* (abstract or otherwise) parent class. Interfaces are chosen when you want to guarantee a class supports a certain set of operations, without imposing any particular implementation details or shared code on it.

**Traits — reuse across unrelated classes.** Inheritance models a strict "is-a" hierarchy — a single line of ancestry. But sometimes unrelated classes (that don't and shouldn't share a common parent) still need the exact same chunk of reusable method code. A trait packages that method implementation separately, and any class can pull it in with `use TraitName;`, gaining those methods as if they'd been written directly in the class — this is sometimes called "horizontal" reuse, as opposed to inheritance's "vertical" reuse.

**Object serialization — turning an object into a storable/transmittable string.** `serialize()` converts an object's current state (its property values, and enough metadata to know which class it belongs to) into a plain string, which can then be stored anywhere a string can go — a session variable, a file, a database column — and later reconstructed with `unserialize()`. The `__sleep()` magic method lets a class control exactly which properties get included in that serialized string (useful for skipping properties that shouldn't or can't be serialized, like an open database connection); `__wakeup()` lets the class run custom setup logic immediately after being reconstructed by `unserialize()`, mirroring what a constructor does for a freshly `new`-created object.

**MVC — a pattern for organising a whole application, not just a class feature.** Model-View-Controller separates an application into three responsibilities: the **Model** owns the data and business logic (what the data *is* and the rules around it); the **View** is purely about presentation (what the user sees); the **Controller** sits between user input and the other two, deciding what should happen in response to a request and coordinating updates. The underlying motivation is separation of concerns: changes to how data is displayed shouldn't require touching the logic that computes it, and vice versa.

## 10. XML/JSON and AJAX

**Why XML exists.** XML (Extensible Markup Language) is a syntax for representing structured, hierarchical data as text, designed to be exchanged between different systems/applications. Unlike HTML, XML has no predefined set of tags — you invent tag names meaningful to your own data — but in exchange, it enforces strict structural rules (every opening tag needs a matching closing tag, proper nesting, etc.), which is what makes it reliably machine-parseable.

**Tree-based vs event-based parsing — a memory/control tradeoff.** A tree-based parser (SimpleXML, DOM) reads the *entire* document into memory upfront as a navigable structure, which is convenient (you can jump around freely) but means the whole document must fit in memory at once. An event-based parser (XMLReader, Expat) instead streams through the document, firing "events" as it encounters each piece, without ever holding the whole thing in memory — better suited to very large XML files where loading everything at once would be impractical.

**SimpleXML vs DOM — convenience vs control.** SimpleXML converts an XML document into an object where each tag essentially becomes a property you can access directly (`$xml->name`), which is fast to write and read for straightforward cases. DOM represents the document in a more literal, lower-level tree that closely mirrors the actual document structure, including details SimpleXML abstracts away (like raw whitespace between tags appearing as its own text nodes) — DOM is the better choice when you need to *build*, heavily modify, or perform detailed structural navigation of XML, at the cost of noticeably more verbose code for simple read operations.

**XPath — searching without manual traversal.** Rather than writing nested loops to walk down an XML tree looking for something, XPath lets you describe *what you're looking for* as a query string (e.g. "any `<meta>` tag anywhere in the document," or "any `<contact>` that has a `<phone type='cell'>` child"), and the parser does the searching. This becomes especially valuable for documents with unpredictable/variable depth or structure, where hardcoding a specific traversal path would be fragile.

**JSON — a lighter alternative to XML for the same underlying problem.** JSON (JavaScript Object Notation) represents structured data as nested objects (`{key: value}`) and arrays (`[...]`), and has become the dominant format for web APIs specifically because it's more compact than XML, maps naturally onto data structures most programming languages already have (objects/arrays), and is directly usable in JavaScript without any parsing step at all (since it *is* JavaScript object syntax).

**json_encode()/json_decode() — the conversion boundary.** `json_encode()` turns a native PHP array/object into a JSON string, for sending elsewhere (an API response, a file, a session). `json_decode()` reverses this. The second argument to `json_decode()` is a genuinely important detail: passing `true` returns an associative array (accessed with `[...]` syntax), while `false` or omitting it returns a plain PHP `object` (accessed with `->` syntax) — the *same* underlying JSON data, represented as two different PHP shapes depending on what's more convenient for the calling code.

**AJAX — updating a page without reloading it.** Ordinarily, any interaction with a server (submitting a form, following a link) triggers a full page reload — the browser discards the current page and renders a fresh one. AJAX (Asynchronous JavaScript And XML — though in practice it almost always carries JSON, not XML, today) uses JavaScript's `XMLHttpRequest` object to send a request to the server *in the background*, receive a response, and update only *part* of the existing page via the DOM — the rest of the page (and its JavaScript state, scroll position, etc.) is left completely untouched. "Asynchronous" is the operative word: the browser doesn't freeze waiting for the response; it continues running, and a callback function handles the response whenever it eventually arrives.

**readyState and status — why both must be checked.** `readyState` describes how far the request has progressed through its lifecycle (0 = not started, ..., 4 = fully complete, response available) — checking `readyState == 4` ensures the response has actually fully arrived, not partially. `status` is the HTTP status code of that completed response (200 = success, 404 = not found, 500 = server error, etc.) — checking `status == 200` ensures the completed request was actually *successful*, not a completed-but-failed request (like a 404). Checking `readyState` alone would let you act on an error response as if it were valid data; checking only `status` without confirming `readyState == 4` risks reading a status value before the response is actually ready. Both together are needed to safely say "the request is finished, and it succeeded."

**Why the PHP side of an AJAX endpoint looks like an ordinary script.** The PHP script handling an AJAX request (e.g. `gethint.php`) has no special AJAX-specific code — it just reads input (from `$_GET`/`$_POST` as normal) and echoes a response (plain text, HTML fragment, or JSON). The "AJAX-ness" of the interaction is entirely a property of how the *JavaScript* on the client side chose to call it (in the background, without a page reload) — the server-side script is functionally indistinguishable from one that outputs a normal full page.

## 11. Recursion and Data Structures

**What makes a function recursive.** A recursive function is one that calls itself, directly or indirectly, as part of computing its own result. This is a natural fit for problems that are *self-similar* — where solving a large instance of the problem means solving one or more smaller instances of the exact same problem (e.g. computing `factorial(5)` requires computing `factorial(4)`, which requires `factorial(3)`, and so on).

**The two non-negotiable ingredients.** Every correct recursive function needs (1) a **base case** — a condition simple enough to answer directly, without recursing further, which is what eventually stops the recursion — and (2) a **reduction step** — each recursive call must move the problem strictly closer to that base case (e.g. by decrementing a counter), so the base case is *guaranteed* to eventually be reached. Missing a base case, or a reduction step that doesn't actually converge, produces infinite recursion, which in practice crashes the script once it exhausts available memory/call-stack space.

**Why recursion "feels" different from a loop, mentally.** A loop repeats the *same* code executing in the *same* stack frame, updating variables in place. Recursion instead creates a brand new, independent instance of the function (with its own fresh local variables) for every call — this is why tracing recursive code by hand usually involves drawing a "call stack" diagram: calls go *downward* until the base case is hit, and then results "bubble back up" through each waiting call, being combined (e.g. multiplied, in factorial's case) as they return.

**Static variables as a workaround for state across recursive calls.** Because each recursive call gets fresh local variables by default, a normal local variable can't be used to track something that should persist *across* the whole chain of recursive calls (like "how deep have we gone so far"). Declaring that variable `static` (see section 2) makes it retain its value between calls, giving the recursion a form of shared memory without needing to pass an extra tracking parameter through every single call.

**Why recursion suits nested/self-referential data specifically.** Structures like folder trees (folders containing folders) or XML documents (elements containing elements) are themselves recursively defined — a folder either contains simple files, or it contains more folders, which are themselves just... folders. A recursive function mirrors this shape directly: "process this level, and for anything that's itself a nested instance of the same structure, recurse into it," which naturally handles any depth of nesting without needing to know that depth in advance.

**Abstract Data Types (ADTs) vs concrete data structures — the distinction.** An ADT (List, Stack, Queue, Tree, Graph, etc.) describes a *conceptual* model — what operations are available and what behaviour they guarantee — without specifying exactly how it's implemented internally. A data structure is the actual, concrete implementation of that model (e.g. "a stack implemented using a plain PHP array with push/pop restricted to one end"). This distinction matters because the same ADT (say, a Stack) could be implemented multiple different ways internally while still honouring the same external behaviour contract.

**Stack (LIFO) vs Queue (FIFO) — opposite access disciplines.** A stack only allows adding/removing from *one* end (conceptually "the top") — Last-In-First-Out, like a stack of plates where you can only take from the top. A queue adds at one end and removes from the *other* — First-In-First-Out, like people lining up. These aren't arbitrary — they model two genuinely different real-world access patterns (undo history is stack-like; a print queue or task queue is queue-like), and choosing the right one for a problem depends on which order items should actually be processed.

**Trees — hierarchical, non-linear structure.** Unlike a list/stack/queue (all linear — one thing after another), a tree branches: each node can have multiple children, forming a hierarchy with a single root and no cycles (there's exactly one path from the root to any given node). A *binary* tree specifically restricts each node to at most two children (conventionally "left" and "right"). Trees are naturally recursive in definition: a tree is a root node plus a collection of subtrees, each of which is itself a valid (smaller) tree — which is exactly why tree traversal is almost always written recursively.

**Graphs — the more general structure.** A graph generalises trees by dropping the restrictions: any vertex can connect to any number of other vertices, connections (edges) can be directed (one-way) or undirected (two-way), and cycles are allowed (a path can loop back on itself). This generality makes graphs suitable for modelling things trees can't — social networks, road maps, dependency relationships — but also means graph algorithms typically need to explicitly track "have I already visited this node" to avoid infinite loops around a cycle, a problem trees don't have.

**Representing a graph — matrix vs list, a memory tradeoff.** An adjacency *matrix* records, for every possible pair of vertices, whether a connection exists (using a full grid of 0s/1s or weights) — simple and offers instant "are these two connected?" lookups, but wastes memory when most possible connections *don't* exist (a "sparse" graph). An adjacency *list* instead stores, per vertex, just the list of vertices it's actually connected to — more memory-efficient for sparse graphs, at the cost of a slightly slower "are these two specifically connected" check (you have to scan that vertex's list rather than doing a direct lookup).

**Weighted graphs.** A plain graph only records *whether* a connection exists. A weighted graph (a "network") additionally attaches a cost/distance/value to each edge — used whenever the *strength* or *cost* of a connection matters, not just its existence, such as finding the cheapest or shortest route between two points.

**Why SPL exists.** The Standard PHP Library provides tested, ready-made implementations of common data structures (stacks, queues, heaps, doubly linked lists, etc.) built into core PHP, so developers don't need to hand-roll their own Stack/Queue classes (as done for learning purposes) in real production code — trading a small amount of learning value for reliability and reduced duplicated effort.
